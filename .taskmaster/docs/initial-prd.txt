# QueueBox - Product Requirements Document

## Overview

QueueBox is a Kotlin-based sidecar/service that provides transactional outbox and inbox patterns for any application, with pluggable message broker support.

### Problem Statement

**Outbox Problem:** Applications need to save data AND publish events atomically. Without the outbox pattern, you get "database saved but event lost" or "event sent but database rolled back" bugs.

**Inbox Problem:** Applications receive webhooks/messages that may be delivered multiple times. Without the inbox pattern, you get duplicate charges, double emails, etc.

### Solution

QueueBox runs as a sidecar alongside any application. The app writes to an outbox table in its own transaction, and QueueBox reliably delivers those messages. For incoming webhooks, QueueBox receives them, deduplicates by idempotency key, and stores in an inbox table for the app to process.

## Tech Stack

- **Language:** Kotlin 2.0+
- **HTTP Framework:** Ktor (coroutines-native, lightweight)
- **Database:** PostgreSQL (FOR UPDATE SKIP LOCKED for polling)
- **Configuration:** YAML with kotlinx.serialization
- **Build:** Gradle multi-module with Kotlin DSL
- **Containerization:** Docker

## Database Schema

### Outbox Table (app writes here)
```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    topic TEXT NOT NULL,
    key TEXT,
    payload JSONB NOT NULL,
    state TEXT DEFAULT 'pending',  -- pending, processing, sent, failed, dead
    attempt INT DEFAULT 0,
    max_attempts INT DEFAULT 5,
    scheduled_at TIMESTAMPTZ DEFAULT NOW(),
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_outbox_pending ON outbox(scheduled_at) WHERE state = 'pending';
```

### Inbox Table (QueueBox writes here, app reads)
```sql
CREATE TABLE inbox (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    event_type TEXT,
    payload JSONB NOT NULL,
    state TEXT DEFAULT 'pending',  -- pending, processing, processed, failed
    created_at TIMESTAMPTZ DEFAULT NOW(),
    processed_at TIMESTAMPTZ,
    UNIQUE(source, idempotency_key)
);

CREATE INDEX idx_inbox_pending ON inbox(created_at) WHERE state = 'pending';
```

      idempotency_key: "$.messageId"

## MVP Requirements (Phase 1)

### 1. Core Domain Models

Create the foundational data classes and interfaces in the `core` module:

- `OutboxMessage` data class with all fields from schema
- `InboxMessage` data class with all fields from schema
- `MessageState` sealed class/enum (Pending, Processing, Sent, Failed, Dead)
- `Destination` sealed interface (HttpDestination, RabbitMQDestination)
- `Publisher` interface with `suspend fun publish(message: OutboxMessage): Result<Unit>`
- `InboxReceiver` interface for receiving messages

### 2. Configuration System

Implement YAML configuration loading in the `config` module:

- Use kotlinx.serialization with YAML format
- Create data classes matching the YAML structure above
- Support environment variable substitution (e.g., `${DB_PASSWORD}`)
- Validate configuration on startup
- Load from file path or classpath resource

### 3. PostgreSQL Repository Layer

Implement database operations in the `postgres` module:

- Use HikariCP for connection pooling
- Use Exposed or raw JDBC with coroutines
- **OutboxRepository:**
  - `claimBatch(batchSize: Int): List<OutboxMessage>` using FOR UPDATE SKIP LOCKED
  - `markSent(id: UUID)`
  - `markFailed(id: UUID, error: String)`
  - `scheduleRetry(id: UUID, delayMs: Long)`
  - `markDead(id: UUID)`
- **InboxRepository:**
  - `store(message: InboxMessage): Result<Unit>` (handles duplicate key)
  - `claimPending(batchSize: Int): List<InboxMessage>`
  - `markProcessed(id: UUID)`
  - `markFailed(id: UUID, error: String)`

### 4. Outbox Polling Service

Implement the outbox processor in the `outbox-service` module:

- Poll loop using coroutines (configurable interval)
- Claim batch of pending messages using FOR UPDATE SKIP LOCKED
- Route messages to appropriate destination based on topic matching
- Support glob pattern matching for topics (e.g., "order.*")
- Implement retry with exponential backoff
- Move to dead letter after max attempts
- Graceful shutdown handling

### 5. HTTP Destination Publisher

Implement HTTP publishing in the `outbox-service` module:

- Use Ktor client for HTTP calls
- POST payload to configured URL + path
- Include headers: Content-Type, X-Topic, X-Message-Id, X-Attempt
- Handle timeouts and HTTP errors
- Return success on 2xx, failure otherwise

### 6. Inbox HTTP Receiver

Implement webhook receiver in the `inbox-service` module:

- Ktor route for configured paths (e.g., POST /webhooks/incoming)
- Extract idempotency key from payload using JSONPath expression
- Store in inbox table with deduplication (unique constraint handles duplicates)
- Return 200 OK immediately (fire-and-forget for sender)
- Return 409 Conflict if duplicate (optional, could also return 200)

### 7. Main Application

Wire everything together in the `app` module:

- Load configuration
- Initialize database connection pool
- Create repository instances
- Start outbox polling coroutine
- Start Ktor server for inbox endpoints
- Health check endpoint (GET /health)
- Metrics endpoint (GET /metrics) - basic counts
- Graceful shutdown on SIGTERM

### 8. Docker Support

Create Docker configuration:

- Multi-stage Dockerfile (build + runtime)
- Use Eclipse Temurin JRE base image
- Expose port 8080
- Health check configuration
- docker-compose.yml for local development with Postgres

## MVP Requirements (Phase 2 - RabbitMQ)

### 9. RabbitMQ Publisher

Implement RabbitMQ publishing in the `rabbitmq` module:

- Use RabbitMQ Java client with Kotlin coroutines wrapper
- Connection management with automatic reconnection
- Declare exchange on startup (configurable type: direct, topic, fanout)
- Publish with routing key (support template: "{{ topic }}")
- Publisher confirms for reliability
- Implement Publisher interface from core module

### 10. RabbitMQ Consumer for Inbox

Implement RabbitMQ consumption in the `rabbitmq` module:

- Consume from configured queue
- Extract idempotency key using JSONPath
- Store in inbox table (same deduplication as HTTP)
- Manual acknowledgment after successful store
- Requeue on failure with delay (using dead-letter exchange)

## Non-Functional Requirements

### Performance
- Handle 1000+ messages/second throughput
- Sub-100ms latency for inbox HTTP receiver
- Efficient batch processing to minimize database round trips

### Reliability
- At-least-once delivery guarantee for outbox
- Exactly-once processing for inbox (via idempotency)
- No message loss on crashes (database is source of truth)
- Graceful degradation when destinations are unavailable

### Observability
- Structured logging with correlation IDs
- Prometheus metrics for monitoring
- Health check endpoints

### Operations
- Single Docker container deployment
- Configuration via YAML file or environment variables
- Zero-downtime deployments supported

## Technical Notes

### FOR UPDATE SKIP LOCKED Pattern
```sql
SELECT * FROM outbox
WHERE state = 'pending' AND scheduled_at <= NOW()
ORDER BY scheduled_at
LIMIT 100
FOR UPDATE SKIP LOCKED
```
This allows multiple QueueBox instances to process without conflicts.

### Idempotency Key Extraction
Use JSONPath (e.g., `$.id`, `$.data.messageId`) to extract the idempotency key from incoming payloads. This provides flexibility for different webhook formats.

### Retry Strategy
Exponential backoff: delay = base_delay * 2^attempt
Max attempts configurable (default 5)
After max attempts, move to 'dead' state for manual review
